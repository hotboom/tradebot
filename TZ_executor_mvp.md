# ТЗ: Executor-бот для торговли по сигналам ликвидаций (MVP)

## 1. Назначение

Сервис принимает сигналы о каскадах ликвидаций от внешнего источника по HTTP,
и при превышении заданного порога открывает рыночную позицию на Bybit Futures в направлении,
противоположном ликвидированной стороне.

## 2. Входной сигнал

Сервис принимает HTTP POST запрос с телом в формате JSON, соответствующим интерфейсу:

```typescript
export interface CascadeSignal {
  symbol: string;            // например "BTCUSDT"
  direction: "LONG" | "SHORT"; // какая сторона была ликвидирована
  totalVolumeUsdt: number;   // суммарный объём ликвидации в USDT
  orderCount: number;        // количество ордеров в каскаде
  lastBankruptcyPrice: number; // цена последней ликвидации в каскаде
  windowMs: number;          // ширина окна каскада в мс
  timestamp: number;         // unix ms времени сигнала
}
```

Эндпоинт: `POST /signal/liquidation`, слушает только `127.0.0.1`, порт задаётся в конфиге.
Авторизации на MVP-этапе нет — доступ ограничен привязкой к `127.0.0.1` (сервис не виден
снаружи VPS). Может быть добавлена позже, если на сервере появятся процессы, способные
случайно или намеренно обратиться на этот порт.

Валидация тела запроса — по схеме, соответствующей `CascadeSignal` (Zod). Некорректный
JSON или несоответствие схеме — `400`, тело сигнала логируется как `rejected` с причиной
`invalid_schema`.

## 3. Логика принятия решения

При получении валидного сигнала:

1. Проверить `totalVolumeUsdt >= config.trading.minLiquidationUsdt` (порог общий для всех
   символов, задаётся в конфиге, см. п.5). Если меньше — сигнал отклоняется, логируется
   с причиной `below_threshold`.
2. Определить направление сделки (сделка открывается в ту же сторону, что и
   ликвидированные позиции):
   - `direction === "LONG"` (ликвидированы лонги) → открыть **Buy** (лонг)
   - `direction === "SHORT"` (ликвидированы шорты) → открыть **Sell** (шорт)
3. Проверка на уже открытую позицию по символу не выполняется — в MVP допускается
   открытие новой позиции на каждый принятый сигнал, независимо от того, сколько позиций
   по этому символу уже открыто. Ограничением служит только доступный баланс на аккаунте:
   если маржи не хватает, Bybit отклонит ордер с ошибкой — это обрабатывается как обычная
   ошибка исполнения (см. п.4, `status: failed`), процесс не падает.
4. Если сигнал прошёл проверку порога — перейти к расчёту параметров ордера.

Фильтров по RSI/StochRSI, sizing по силе сигнала и risk-guard'ов по дневной просадке
в MVP **нет** — они вне рамок этой версии и будут добавлены позже.

## 4. Исполнение ордера

- Инструмент: **Bybit Futures** (`category: linear`), символ берётся из `signal.symbol` как есть.
- Тип ордера: **Market**.
- Размер позиции: фиксированный, берётся из конфига (`config.positionSizeUsdt` — минимальный
  и одновременно единственный размер позиции в MVP, без динамического sizing).
- Плечо: выставляется перед открытием позиции через `setLeverage`, значение из
  `config.leverage` (общее для всех символов в MVP).
- Перед открытием позиции выставить плечо на бирже (если ещё не выставлено для символа/аккаунта).
- Сразу при открытии позиции задать `stopLoss` и `takeProfit` в параметрах ордера
  (Bybit v5 позволяет передать `stopLoss`/`takeProfit` прямо в `submitOrder`) — **опционально**,
  если заданы в конфиге (см. п.5):
  - `config.trading.stopLossPercent` и `config.trading.takeProfitPercent` имеют тип
    `number | null`. Если значение `null` (или поле отсутствует) — соответствующий параметр
    (`stopLoss` и/или `takeProfit`) просто не добавляется в объект ордера, позиция
    открывается без него.
  - Если значение задано, SL/TP рассчитываются от цены входа:
    - Для Buy (сигнал `LONG` — ликвидированы лонги): `SL = entryPrice * (1 - stopLossPercent / 100)`,
      `TP = entryPrice * (1 + takeProfitPercent / 100)`
    - Для Sell (сигнал `SHORT` — ликвидированы шорты): `SL = entryPrice * (1 + stopLossPercent / 100)`,
      `TP = entryPrice * (1 - takeProfitPercent / 100)`
  - SL и TP настраиваются независимо друг от друга — можно задать только один из них.
  - Так как ордер маркет, точная цена входа известна только по факту исполнения — в MVP
    допустимо ориентировочно считать `entryPrice` от последней цены (`lastBankruptcyPrice`
    из сигнала или текущий тикер), т.к. Bybit принимает SL/TP как абсолютные цены при
    создании ордера. Отклонение из-за проскальзывания в рамках MVP считается приемлемым.
- Идемпотентность: перед отправкой ордера в БД/файл проверяется уникальность сигнала
  (по паре `symbol + timestamp` или хэшу сигнала), чтобы исключить дублирование при
  повторной отправке от источника.

## 5. Конфигурация

Файл конфигурации (JSON), например `config.json`:

```json
{
  "server": {
    "port": 4001,
    "host": "127.0.0.1"
  },
  "bybit": {
    "testnet": true,
    "leverage": 5
  },
  "trading": {
    "minLiquidationUsdt": 1000000,
    "positionSizeUsdt": 100,
    "stopLossPercent": 1.5,
    "takeProfitPercent": null
  },
  "logging": {
    "signalsLogPath": "./logs/signals.log",
    "ordersLogPath": "./logs/orders.log"
  }
}
```

Примечания:
- `minLiquidationUsdt` — единый порог на MVP-этапе (без разбивки по символам).
- `positionSizeUsdt` — минимальный/единственный размер позиции в MVP (задаётся в USDT
  номинала позиции, конвертация в `qty` контракта — внутри executor'а на основе текущей
  цены и шага лота инструмента).
- `leverage` — общее плечо для всех сделок.
- `stopLossPercent` / `takeProfitPercent` — опциональны (`number | null`). Чтобы открывать
  позицию без стоп-лосса или без тейк-профита — указать `null` (или убрать поле из JSON,
  тогда при чтении конфига оно тоже трактуется как `null`). Работают независимо друг
  от друга.
- API-ключ/секрет Bybit — **не в конфиге**, только через переменные окружения
  (`BYBIT_API_KEY`, `BYBIT_API_SECRET`).

## 6. Логирование

Два отдельных файла (append-only, построчный JSON — JSON Lines):

### 6.1 Лог сигналов — `signals.log`

Пишется запись на **каждый** входящий сигнал, независимо от решения:

```json
{"ts":1720000000000,"eventTs":1720000000000,"symbol":"BTCUSDT","direction":"LONG","totalVolumeUsdt":4200000,"orderCount":12,"lastBankruptcyPrice":63500,"windowMs":5000,"decision":"accepted","reason":null}
```

Возможные значения `decision`: `accepted`, `rejected`.
Возможные значения `reason` (при rejected): `invalid_schema`, `below_threshold`.

### 6.2 Лог ордеров — `orders.log`

Пишется запись при каждой попытке отправки ордера на биржу (успех или ошибка):

```json
{"ts":1720000000000,"symbol":"BTCUSDT","side":"Buy","qty":0.0015,"leverage":5,"entryPriceRef":63500,"sl":62552.5,"tp":65405,"status":"filled","bybitOrderId":"xxxx","error":null}
```

Возможные значения `status`: `submitted`, `filled`, `failed`.
При `failed` — заполняется `error` (текст ошибки/код ответа Bybit).

## 7. Стек

- Node.js 20+ / TypeScript
- Fastify — HTTP сервер приёма сигналов
- Zod — валидация входящего сигнала по схеме `CascadeSignal`
- `bybit-api` (RestClientV5) — исполнение ордеров, установка плеча
- PM2 — процесс-менеджер на VPS
- Файловое логирование (JSON Lines), без БД в рамках MVP

## 8. Структура проекта

```
executor-service/
  src/
    server.ts              // Fastify, роут /signal/liquidation
    config.ts               // загрузка и валидация config.json
    schema/
      cascadeSignal.ts       // Zod-схема CascadeSignal
    decision/
      filters.ts              // проверка порога и открытой позиции
      exits.ts                 // расчёт SL/TP
    bybit/
      client.ts                // обёртка над RestClientV5
      leverage.ts               // установка плеча
    logging/
      signalsLogger.ts
      ordersLogger.ts
    types.ts
  config.json
  .env                      // BYBIT_API_KEY, BYBIT_API_SECRET
  package.json
```

## 9. Вне рамок MVP (следующие итерации)

- Фильтры по RSI / StochRSI
- Динамический sizing позиции по силе сигнала
- Risk-guard: лимит дневной просадки, суммарной экспозиции по всем символам
- Хранение сигналов/ордеров в MySQL вместо файлов
- Приём сигналов из нескольких источников (pump-scanner и др.) с разными схемами
- Умное управление позицией: усреднение/наращивание с учётом текущей экспозиции,
  ограничение максимального количества/объёма открытых позиций по символу
- Дашборд/мониторинг поверх логов

## 10. Критерии приёмки MVP

1. Сервис поднимается на `127.0.0.1:<port>` и принимает POST на `/signal/liquidation`.
2. Запрос с телом, не соответствующим `CascadeSignal`, — `400`, запись в `signals.log`
   с `decision: rejected, reason: invalid_schema`.
3. Сигнал с `totalVolumeUsdt` ниже порога — запись в `signals.log` с
   `decision: rejected, reason: below_threshold`, ордер не создаётся.
4. Сигнал с `totalVolumeUsdt` выше порога и `direction: LONG` — открывается Market Buy
   на фьючерсах по символу из сигнала (та же сторона, что и ликвидированные позиции),
   с плечом из конфига, SL/TP выставлены согласно проценту из конфига, запись в `orders.log`.
5. Сигнал с `direction: SHORT` — аналогично, но Market Sell.
6. Ошибка при вызове Bybit API (например, недостаточно баланса/маржи) — запись в
   `orders.log` со `status: failed` и текстом ошибки, процесс не падает.
7. Тестирование выполнено на `testnet: true` перед переключением на боевой режим.
