# Executor-сервис (MVP)

Принимает сигналы о каскадах ликвидаций по HTTP и открывает рыночные позиции
на Bybit Futures (`category: linear`) при превышении порога объёма.

## Установка

```bash
npm install
cp .env.example .env      # прописать BYBIT_API_KEY / BYBIT_API_SECRET
cp config.example.json config.json   # порт, testnet, порог, размер позиции, SL/TP
```

Настройки — в `config.json` (не в git; шаблон — `config.example.json`).
Плечо сервис не выставляет — используется то, что уже задано на аккаунте Bybit для символа.

## Запуск

```bash
# режим разработки
npm run dev

# сборка + запуск
npm run build
npm start
```

На проде одного `npm install` недостаточно — нужна сборка (`dist/` не хранится в git) и
запуск через **PM2**, чтобы процесс жил в фоне и перезапускался при падении.

## Деплой на VPS (прод)

### Первый раз на сервере

```bash
# Node.js 20+
node -v

git clone <ваш-репо> tradebot
cd tradebot

npm install

# .env в git нет — создать вручную на сервере
cp .env.example .env
# прописать BYBIT_API_KEY / BYBIT_API_SECRET

# порт, testnet: false, пороги, размер позиции, SL/TP
cp config.example.json config.json
nano config.json

npm run build

npm install -g pm2
pm2 start ecosystem.config.js

# автозапуск после перезагрузки VPS
pm2 save
pm2 startup   # выполнить команду, которую выведет pm2
```

Сервис слушает `127.0.0.1:4001` — снаружи не виден. Сигналы шлёт другой процесс
на том же VPS (сканер ликвидаций и т.п.) через HTTP на localhost.

### После каждого `git pull`

```bash
cd tradebot
git pull
npm install          # если менялись зависимости
npm run build        # обязательно — dist/ не в репозитории
```

`.env` и `config.json` pull не трогает (не в git). После pull достаточно `npm install` + `npm run build` + `pm2 restart`.
Если в репозитории появились новые поля конфига — сверить с `config.example.json` и дописать в локальный `config.json` вручную.


## API

`POST http://127.0.0.1:4001/signal/liquidation`

```json
{
  "symbol": "BTCUSDT",
  "direction": "LONG",
  "totalVolumeUsdt": 4200000,
  "orderCount": 12,
  "lastBankruptcyPrice": 63500,
  "windowMs": 5000,
  "timestamp": 1720000000000
}
```

- Некорректная схема — `400`, запись в `signals.log` (`rejected` / `invalid_schema`).
- Объём ниже `trading.minLiquidationUsdt` — `200`, запись `rejected` / `below_threshold`, ордер не создаётся.
- Валидный сигнал выше порога — `200`, вход Buy (сигнал `LONG`) или Sell (`SHORT`) на объём
  `trading.positionSizeUsdt`; результат — в `orders.log`.
- Повторный сигнал (тот же `symbol` + `timestamp`) не создаёт дубликат ордера (идемпотентность
  по `logs/processed_signals.log`).

### Вход: market или limit-чейз (`trading.entryOrderType`)

- `"market"` (по умолчанию) — маркет-ордер, без задержки.
- `"limit"` — вход пассивным лимитником по лучшей цене своей стороны стакана (best bid для
  Buy / best ask для Sell), чтобы платить maker-комиссию. Если цена уходит и ордер не
  наполняется — бот сам перевыставляет его на новую лучшую цену (`src/bybit/limitChaseEntry.ts`).
  Таймаута нет: чейз ждёт полного исполнения сколько потребуется, маркет-фоллбэка не делает.

### Стоп-лосс: market, limit + backup (`trading.stopLossOrderType`)

- `"market"` (по умолчанию) — обычный SL, гарантированно исполняется, но с taker-комиссией.
- `"limit"` — SL выставляется лимитным ордером (дешевле по комиссии), и на этот случай
  дополнительно ставится независимый **резервный market SL** чуть дальше основного
  (`SL_BACKUP_BUFFER_MULTIPLIER` в `src/executor.ts`) — страховка на случай, если лимитный SL
  не успеет исполниться при резком движении. Если лимитный SL не встал на бирже вообще (например,
  недостаточно ликвидности по цене) — бот сразу переключается на обычный market SL.

Постановка и любая последующая замена SL идут через общий `replacePositionStop()`
(`src/decision/riskOrders.ts`) — см. раздел «Замена стопа: place-before-cancel» ниже.

### Усреднение позиции (повторные сигналы по одному символу)

Ничего не мешает нескольким сигналам по одному символу открыться друг за другом — аккаунт
торгует в one-way режиме, поэтому каждый новый вход просто добавляется к уже открытой позиции
(пирамидинг/усреднение). При каждом входе (первом и последующих) бот:

1. Берёт с биржи **фактические среднюю цену и полный текущий объём позиции** (не цену/объём
   только что открытого входа) и считает SL/TP от них.
2. Полностью пересоздаёт SL/TP на весь объём позиции. SL пересоздаётся по схеме
   **place-before-cancel** (см. ниже): сначала ставится новый SL (+ резервный market-SL),
   и только после подтверждения снимаются старые условные ордера риск-менеджмента по символу
   (Partial SL позиции и прошлый backup market-SL). Легаси `PartialTakeProfit` не трогается —
   TP теперь живёт отдельным reduce-only лимитником, который пересоздаётся под новый объём
   позиции своей отдельной отменой. На бирже в итоге не остаётся больше одной актуальной пары
   SL/TP и одного backup-ордера на символ (без явной отмены Bybit не заменяет Partial SL при
   повторном вызове, а добавляет новый поверх — поэтому на короткое время между шагами у
   позиции может висеть два Partial SL, оба reduce-only).
3. Сигналы по одному символу обрабатываются строго по очереди (`OrderExecutor` сериализует
   `execute()` по `symbol`) — если второй сигнал по тому же символу приходит, пока первый ещё
   выполняется (например, идёт лимитный чейз), он ждёт завершения первого, чтобы не читать
   промежуточное/гоночное состояние позиции. Сигналы по разным символам друг друга не блокируют.

### Замена стопа: place-before-cancel (`src/decision/riskOrders.ts`)

Любая замена SL уже открытой позиции (усреднение в `executor.ts`, перенос в безубыток,
trailing) идёт через общий `replacePositionStop()`, чтобы позиция никогда не оставалась без
защиты:

1. **Сначала ставится новый SL** — `setTradingStop` в `tpslMode: "Partial"` желаемым типом
   (Limit), при отказе биржи — фоллбэк на Market.
2. Если новый SL остался лимитным — ставится независимый резервный **market**-SL чуть дальше.
3. **Только теперь** отменяются старые ордера риск-менеджмента (прошлый Partial SL + прошлый
   backup market-SL), которые были прочитаны с биржи **до** шага 1.
4. Если новый SL не удалось поставить **ни лимитом, ни маркетом** — функция бросает ошибку,
   **не тронув старые ордера**: позиция остаётся под защитой прежнего стопа. Вызывающий код
   пишет `failed` в свой лог (`... — прежний SL сохранён`).

Раньше порядок был обратный (сначала отмена, потом установка) — при отказе Bybit на шаге
установки позиция оставалась совсем без стопа (инцидент BNCUSDT 2026-09-08: SL сняли, новый
отбило `retCode 10001`, дальше каждый тик мониторов бился в тот же отказ).

**Проверка стороны цены.** Оба монитора перед заменой берут текущую `lastPrice`
(`getLastPrice`) и через `stopLossOnValidSide()` проверяют, что новый SL вообще можно
отправить на биржу: для шорта он должен быть строго выше текущей цены, для лонга — строго
ниже (иначе Bybit отбивает `setTradingStop` с `retCode 10001 ... should greater/less
base_price ... LastPrice`). Кандидат считается от `markPrice` из снапшота позиции, и на резко
пилящем рынке (тот же каскад ликвидаций, что породил сигнал) он легко оказывается уже не с
той стороны — в этом случае монитор просто **пропускает тик, не трогая существующий стоп**, и
ждёт следующего с актуальной ценой.

### Перенос стопа в безубыток (`trading.breakevenEnabled`)

Фоновый монитор (`src/breakevenMonitor.ts`), работающий отдельно от входа/SL/TP по сигналу:

- Включается `trading.breakevenEnabled` (по умолчанию выключен).
- Раз в `trading.breakevenCheckIntervalSec` секунд (по умолчанию 60) проверяет **все** открытые
  позиции аккаунта. Первая проверка — не сразу после входа, а через один интервал: короткий
  всплеск волатильности в момент входа не должен переносить стоп раньше времени.
- Как только позиция в плюсе минимум на `trading.breakevenTriggerPercent` % (по умолчанию 1%)
  от цены входа (`avgPrice`, сравнение с `markPrice`), переносит её стоп-лосс в безубыток —
  на цену входа, скорректированную на комиссию биржи в обе стороны (taker-комиссия символа,
  `GET /v5/account/fee-rate`, ×2 на вход и выход) плюс `trading.breakevenExtraProfitPercent` %
  (по умолчанию 0.1%) сверху, чтобы срабатывание нового стопа не только не увело сделку в
  минус, но и гарантированно закрыло её в небольшой плюс — иначе на практике (проскальзывание,
  реальная комиссия закрытия) сделка часто закрывается чуть в минусе даже при формально точном
  безубытке. Стоп выставляется **Limit**-ордером (дешевле по комиссии), плюс независимый
  резервный **market**-SL чуть дальше — на случай, если лимитник не успеет исполниться при
  резком движении (тот же приём, что и для основного SL, см. `SL_BACKUP_BUFFER_MULTIPLIER`).
  Если лимитный SL не встал на бирже вообще — бот сразу переключается на обычный market SL
  (без резервного ордера — market и так исполняется немедленно). Замена идёт через
  `replacePositionStop()` (place-before-cancel + проверка стороны цены, см. выше) — при отказе
  биржи прежний стоп остаётся на месте.
- Если стоп уже на безубытке или лучше — монитор его не трогает (не отодвигает назад и не
  дёргает биржу на каждом тике). Сверяется при этом не с полем `stopLoss`/`takeProfit` самой
  позиции (`getPositionInfo`) — в `tpslMode: "Partial"`, который бот всегда использует, Bybit
  туда SL/TP позиции не пишет, это независимые резидентные ордера (`PartialStopLoss`/
  `PartialTakeProfit`) — а с фактическими условными ордерами на бирже (`getOpenStopOrders`).
- Если открытых позиций нет — монитор останавливается сам (таймер снимается) и не делает
  запросов к бирже до следующего открытия позиции. Запускается заново автоматически при каждом
  успешном входе (`executor.ts`) и при старте процесса (на случай рестарта pm2 с уже открытой
  позицией).
- Результат каждой попытки переноса — в `logs/breakeven.log` (`applied` / `failed`).

### Trailing-stop (`trading.trailingEnabled`)

Фоновый монитор (`src/trailingStopMonitor.ts`), устроен так же, как монитор безубытка выше,
но с независимыми настройками и другой логикой стопа:

- Включается `trading.trailingEnabled` (по умолчанию выключен).
- Раз в `trading.trailingCheckIntervalSec` секунд (по умолчанию 60) проверяет **все** открытые
  позиции аккаунта. Первая проверка — не сразу после входа, а через один интервал (как и у
  монитора безубытка): в первые миллисекунды позиции цена в разгар каскада ликвидаций
  ненадёжна, и стоп по такой цене дёргать нельзя.
- Как только позиция в плюсе минимум на `trading.trailingTriggerPercent` % (по умолчанию 5%) от
  цены входа, начинает подтягивать стоп-лосс вслед за ценой — на `trading.trailingStopPercent`
  % (по умолчанию 1%) хуже **текущей** цены (`markPrice`), а не цены входа, как в безубытке —
  классический trailing-stop.
- Стоп двигается только в сторону прибыли: если цена откатывается против позиции, новый кандидат
  оказывается хуже уже выставленного стопа, и монитор его не трогает — стоп остаётся на лучшей
  достигнутой точке. Если цена продолжает идти в нужную сторону — стоп на каждом тике
  подтягивается ближе.
- Ордера — та же схема, что и в безубытке: **Limit** (дешевле по комиссии) + независимый
  резервный **market**-SL чуть дальше (`SL_BACKUP_BUFFER_MULTIPLIER`), с фоллбэком на обычный
  market SL, если лимитник не встал. Замена — через `replacePositionStop()` (place-before-cancel
  + проверка стороны цены, см. выше): если на пилящем рынке кандидат оказался не с той стороны
  текущей цены или биржа отбила установку — прежний стоп сохраняется, тик пропускается.
- Работает независимо от монитора безубытка (свои enable/trigger/interval), но оба монитора и
  исполнитель входа сериализуют доступ к условным ордерам позиции по символу через общую очередь
  (`src/util/symbolQueue.ts`) — так как оба мотора только подтягивают стоп вперёд и никогда не
  отодвигают его назад, можно смело включать оба сразу: чей стоп ближе к прибыли, тот и остаётся.
- Если открытых позиций нет — монитор останавливается сам, как и монитор безубытка. Запускается
  заново автоматически при каждом успешном входе и при старте процесса.
- Результат каждой попытки — в `logs/trailing.log` (`applied` / `failed`).

## Логи

JSON Lines, append-only:

- `logs/signals.log` — каждый входящий сигнал с решением (`accepted` / `rejected` + причина);
- `logs/orders.log` — каждая попытка отправки ордера (`filled` / `failed` + ошибка);
- `logs/breakeven.log` — каждая попытка переноса стопа в безубыток (`applied` / `failed`);
- `logs/trailing.log` — каждая попытка подтянуть trailing-stop (`applied` / `failed`);
- `logs/processed_signals.log` — ключи обработанных сигналов (идемпотентность).

## Тестирование

Перед боевым режимом проверять на `"testnet": true` (ключи API — от testnet.bybit.com).
